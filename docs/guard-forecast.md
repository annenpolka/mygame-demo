# 防御が着弾に間に合うかの表示

2026-09-15、ルール版 `orchestra-16`。戦闘コア、所要時間、処理順、保存Stateの形式は変更していない。予約の実行時刻は既存の `planTiming` をそのまま使う。

## 観察

1440×900の周囲メニューで、手動の5戦を録画した。操作はキーボード。

| 戦闘セット・強度 | 操作                                         | 結果                        |
| ---------------- | -------------------------------------------- | --------------------------- |
| 鐘楼の関門・1    | 基本技2回→行動開始の繰り返し                 | 約27秒で勝利                |
| 鐘楼の関門・3    | 同上                                         | 約39秒で勝利                |
| 交差砲火・5      | 同上                                         | 16.1秒で全滅                |
| 交差砲火・5      | 操作キャラへの予告を見たら後続取消→防御→開始 | 24.5秒で全滅                |
| 交差砲火・2      | 同上                                         | 2分15秒で勝利（長い消耗戦） |

録画から次の場面を確認した。

- 交差砲火・強度5の開始4秒で、前列薙ぎ払いと前列への交差砲撃がアルトに重なった。アルトの駒には一番近い「範囲攻撃 1.7秒」だけが出ていた。2発目で戦闘不能になった。
- 交差砲火・強度2の1分32秒。予告を見て防御を確定したが、ATBは0.1で「確定列 1ATB待ち」だった。着弾まで0.2秒で、防御は間に合わない状態だった。戦場にはそれを示す表示がなかった。予約欄の「◷ 秒」は下の操作盤にあり、1440×900ではスクロールが必要だった。着弾時刻とも並べていなかった。
- 基本技の下書きが残ったまま防御を押すと、防御は下書きの末尾に並ぶ。`B`の後続取消は下書きを残す。急いで防御する場合は「後続取消→防御→行動開始」を順に押し、残った下書きも一件ずつ消す必要があった。

## 特定した問題

1. **判断の意味：防御が着弾に間に合うか、判断する時点で分からない。** 仲間AIは`planTiming`で間に合う防御だけを予約する。人間には予告の残り秒だけが見え、ATB不足、硬直、先の予約待ちで遅れることは分からない。防御が失敗しても、判断が悪かったのか、入力が遅かったのかを学べない。
2. **視認性：同じキャラへ重なる予告を1つしか示さない。** 駒の9pxの赤字は一番近い着弾だけを示す。何発来るか、合計で倒れるかは敵の駒をそれぞれ読む必要がある。
3. **操作負荷：予告への防御に3〜4入力が必要で、手順を間違えると遅れる。** 防御は下書きの末尾に入り、後続取消は下書きを残す。予約の時刻と一件取消がある下の操作盤は、横長画面で戦場より下にある。

1が最も重要と判断した。2と3は予告に対応する手間を下げる。一方、1がないと対応の成否を判断材料にできない。1の表示は3の手順の誤りを「予約待ち」として示す。下の再現条件では、予告直後に今の予約のまま防御して間に合うのは80%。1秒後に反応した場合は62%に下がる。

### 反応の余裕の測定

`npx tsx scripts/guard-window-study.ts`。`rush`方針・予約3手、5戦闘セット×強度1・3×seed 1〜3の戦闘を再生する。予告が味方に向いた347件で、そのキャラが防御を入力した場合を判定した。

| 時点         | 今の予約のまま間に合う | 予約を消せば間に合う | ATB・硬直で間に合わない | 1秒以内に着弾済み |
| ------------ | ---------------------- | -------------------- | ----------------------- | ----------------- |
| 予告の出現時 | 279                    | 60                   | 8                       | 0                 |
| 実時間1秒後  | 217                    | 52                   | 57                      | 21                |

同じキャラに別の予告が重なっていたのは59件。AIの予約状態を人間の代わりに使った目安であり、人間の反応速度や誤操作率の実測ではない。

## 実装

手動で操作中のキャラへ予告が向くと、駒の状態行（同じ内容をATB帯の見出しにも表示）を防御の判定に置き換える。対象は、そのキャラに最も早く着弾する予告。

| 表示                    | 意味                                                                |
| ----------------------- | ------------------------------------------------------------------- |
| `防御なら ✓ 間に合う`   | 今`防御`を追加して`行動開始`すると、着弾前に構えが完了する          |
| `開始で防御 ✓ 間に合う` | 下書きの防御を今`行動開始`すれば間に合う                            |
| `防御 ✓ 間に合う`       | 確定済みの防御が間に合う                                            |
| `… ✗ 予約待ち`          | 先に並んだ予約を待つため遅れる。未開始の予約を消せば間に合う        |
| `… ✗ 間に合わない`      | 実行中の行動・硬直とATBの充填を待つため、予約を消しても間に合わない |
| `… ✗ 予約が満杯`        | 防御を追加できない                                                  |
| `防護中 ✓ 軽減`         | 防御・防護の効果中に着弾する                                        |

色だけで区別せず、✓/✗と文字を併記する。titleと駒の読み上げ説明には、着弾までの秒数、構えまでの秒数、遅れる理由を文章で入れる。仲間AIの駒には表示しない。AI鑑賞と録画も変わらない。

判定は`src/client/guard-forecast.ts`。現在のパーティーボーナス込みのATB速度を`planTiming`へ渡し、防御の効果が出るtickと敵の着弾tickを比べる。同じtick内では味方が先に解決する規則も反映した。予約を消した場合は、実行中の行動を残し、防御だけを並べて再計算する。表示用の複製だけを使い、戦闘Stateは変更しない。今後のAI行動、押し出し、ブレイクによる予告の停止は予測しない。

状態行を置き換えるため、駒の情報の高さは変わらない。1366×600のような短い画面でも、周囲・足元メニューへ重ならない。幅800px以下では状態行を隠しているが、この判定だけは予告の残り秒の下に表示する。

## 検証

- `tests/guard-forecast.test.ts`：ATB 0〜2.5、行動中・下書き・確定済みの攻撃、防御なし・下書き・確定、着弾0.3〜4.0秒の0.1秒刻みを組み合わせる。各条件で実際のエンジンを着弾まで進め、軽減の有無が判定と一致することを確認した。「予約待ち」の条件は、未開始の予約を消すと軽減されることも確認した。判定しても戦闘Stateが変わらないことを検査した。
- `tests/e2e/guard-forecast.spec.ts`：`Z Z H`で「防御なら ✗ 予約待ち」、`C`で「開始で防御 ✗ 予約待ち」、`B`で「開始で防御 ✓ 間に合う」、`H`で「防御 ✓ 間に合う」になる。その後「防護中 ✓ 軽減」となり、実際のHP減少が半分になることを確認した。1440×900、1366×752、1366×600、1024×768、900×600、390×844の周囲・足元・下の操作盤で、3人同列のまま切れず、レーンからはみ出さず、メニューのボタンや他の駒に重ならないことを測った。
- 変更後の画面で交差砲火・強度2を再プレイし、表示に従って防御と取消を選んだ。「防御なら ✗ 予約待ち」から取消・防御・開始で「防御 ✓ 間に合う」「防護中 ✓ 軽減」へ移ることを録画で確認した。
